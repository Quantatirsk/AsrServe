# Issue #77：转写标点退化排查

排查日期：2026-10-07（北京时间）。对象：[issue #77](https://github.com/Quantatirsk/AsrServe/issues/77)、`v1.0.3`、`v1.0.4` 和当前 `dev`（`c4eff7e`）。

## 已确认的原因

实测支持：**段内标点退化的主要原因是默认 ASR 从 Qwen3-ASR 切换为 R2T2；删除旧标点模块又去掉了句尾补偿。** 这两个变化影响的范围不同。

- **模型负责段内句读。** 1.0.3 默认使用 Qwen3-ASR，离线 Qwen 路径直接采用模型生成的标点，并没有调用独立 CT-Transformer 恢复整段标点。1.0.4 改用 Confucius4-R2T2，当前离线路径直接保留它的原生句读。
- **删除旧标点模块，直接造成句尾补标点能力丢失。** 被删除的 `restore_sentence_endings()` 只采用标点模型输出的最后一个终止符，明确忽略内部改动。这段代码即使原样恢复，也不能修复一段内部缺少句号、逗号的问题。
- **段落合并放大显示效果。** 同一说话人的文字直接拼接，依赖文本里已有的句号来触发自然段边界。缺少句号时，同一说话人的段落可能到硬上限才分开；这个步骤保留文字和标点，但不生成新的标点。

## 当前服务复现

调查开始时，运行中的 `asrserve-asr-1` 容器，其 `realtime/engine.py` 和 `asr/r2t2_engine.py` 与 `c4eff7e` 工作区文件 SHA-256 一致。对本机已有会议录音前 60 秒，通过 `/v1/audio/transcriptions` 分别启用、关闭说话人分离：

| 模式 | 字符数 | 逗号 | 句号 | 问号/感叹号 |
|---|---:|---:|---:|---:|
| 关闭说话人分离 | 355 | 20 | 0 | 0 |
| 开启说话人分离 | 355 | 20 | 0 | 0 |

两个响应的 `text` 完全相同，输出分段保留了原有逗号。这里复现的是缺少句号的长段；短中文样本能正常返回句号，因此不是全局过滤标点。

对相同的 355 字结果运行 `19b52f2` 删除前的实际句尾恢复函数，输出为 356 字、20 个逗号、1 个句号；最长没有句末标点的连续文本仍为 355 字。

## 同音频、同提示的模型对照

独立加载两个缓存 checkpoint，通过同一运行时使用相同的空系统提示、16 kHz 单声道 float32 音频、BF16 和 greedy 解码，首轮输出上限均为 4096 tokens。Qwen 取原生完整输出；R2T2 同时记录首轮输出和当前服务规定的 0.64 秒静音 lookahead 尾部解码。两边每个样本的 PCM SHA-256 均一致。

| 样本 | Qwen 逗号/句号 | R2T2 逗号/句号 | Qwen 最长无句末标点文本 | R2T2 最长无句末标点文本 |
|---|---:|---:|---:|---:|
| 会议 0–15 秒 | 8 / 2 | 5 / 0 | 60 字 | 90 字 |
| 会议 0–60 秒 | 25 / 9 | 20 / 0 | 82 字 | 355 字 |
| 会议 120–180 秒 | 24 / 6 | 19 / 0 | 86 字 | 341 字 |
| 中文短音频 | 1 / 1 | 1 / 1 | 21 字 | 21 字 |
| 英文短音频 | 2 / 3 | 2 / 1 | 69 字符 | 69 字符 |

三个会议片段中，R2T2 首轮输出就没有句号，尾部解码之后也没有；不是尾部解码或者说话人组装删除了句号。独立 R2T2 的 60 秒结果与当前服务响应逐字一致。

模型 revisions：Qwen3-ASR-1.7B `7278e1e70fe206f11671096ffdd38061171dd6e5`；R2T2 `185ce639118ad1362d049ca0d8ed04b6ec5cd6c9`。运行时为 vLLM 0.30.0、PyTorch 2.13.0+cu130，GPU 为 RTX PRO 6000 Blackwell。此对照使用共同提示以隔离 checkpoint 差异，不是对 1.0.3 的整套旧运行环境做逐位复现。统计句号时排除了数字间的小数点。

## 句尾补偿和全文恢复的区别

完整 CT-Transformer 的诊断实验先移除已有句读，再预测全文标点。在当前服务这段结果上，产生 **17 个逗号、8 个句号**，最长没有句末标点的连续文本降至 **81 字**。逐字符去除标点和空白后，结果与输入的字母、数字和汉字序列完全一致。这证明独立全文恢复可以处理该样本的段内断句，但还需要产品名、小数、混合语言等保护策略才能成为生产修复。

另一个 60 秒会议片段经全文恢复后，从 0 个句号变为 7 个，最长无句末标点文本从 341 字降为 85 字，正文字符序列也保持一致。不过英文样本中，全文恢复将原来的 `but` 改成了 `But`，还插入了前导空格。这里已经实测到文本改写，不能直接把模型返回的全文用于生产；应将标点预测映射回原始 ASR 文本，并验证原始字符完整保留。

直接采用 CT-Transformer 对含标点输入的全文输出，会产生 `，，`、`。，`、`。。`。因此，直接恢复旧模型并替换整个字符串不能作为完整修复。

## 已实现的修复

在离线识别完成后、强制对齐和说话人归属前，调用 CT-Transformer 恢复段内和句尾标点。一次调用按原始顺序提供整份文件的转写字词，让计算块之间共享上下文，再将预测的 `punc_array` 标签映射回各块的原文位置；不用模型重排格式、调整大小写后的 `text` 输出。保留原有句末和结构标点，允许将逗号升级为句号或问号，同时保护空格、英文大小写、数字、小数、时间、版本号及 URL。

复用原有 `iic/punc_ct-transformer_zh-cn-common-vocab272727-pytorch`，固定 ModelScope `v2.0.4`，三个必需文件逐一校验 SHA-256。约 292 MB 的权重在 CPU 上加载，已恢复依赖锁定、自动下载、离线检查、启动预加载和退出释放。

实际修复输出（保留原文中的合理标点，因此与前述直接采用模型格式化全文的诊断数字略有区别）：

| 样本 | 修复前句号 | 修复后句号 | 最长无句末标点文本（前 → 后） |
|---|---:|---:|---:|
| 会议 0–15 秒 | 0 | 1 | 90 → 91 字 |
| 会议 0–60 秒 | 0 | 8 | 355 → 83 字 |
| 会议 120–180 秒 | 0 | 7 | 341 → 87 字 |
| 中文短音频 | 1 | 1 | 21 → 21 字 |
| 英文短音频 | 1 | 3 | 69 → 56 字符 |

去除句读后，五个样本的正文字符、空格和大小写序列均与原始 R2T2 输出相同。模型预热后，两段 60 秒会议文本的标点推理各约 0.26 秒；这是本机 CPU 结果，不包含识别和对齐时间。

验证结果：全套 **170 项测试及 68 个子测试通过**；静态检查、依赖兼容性和 `uv 0.9.22 lock --check` 通过。真实 CUDA 流水线复用了运行中服务的私有 R2T2 引擎，在隔离容器加载强制对齐、Nemotron 和 CPU 标点模型：60 秒音频的说话人分离与词时间戳四种开关组合文字完全一致，均为 8 个句号；5 分钟音频经 119 个计算块恢复后，从 17 个句号变为 37 个句号、2 个问号。验证了整体 `text` 与 `segments` 的文字一致、正文不改写、时间戳有序且在音频范围内。

修复验证证据同样位于 `logs/issue-77-punctuation/`：`fixed-punctuation.json`、`integrated-fixed.json`、`fix-all-tests.log`、`fix-final-targeted.log`、`fix-dependencies.log`、`fix-lock-check.log`，以及对应的验证脚本。运行中的正式服务仍使用原镜像；本次验证未替换它。

仅回退删除标点模块的提交，能恢复片段句尾，不能恢复段内句读。Nemotron 的语音检测职责也不能替代文本标点恢复。

本次没有 issue 报告者的原始录音；实测使用本机已有中文会议录音与中英文短音频。标点数量用于诊断输出行为，不等于人工标注的标点准确率。
